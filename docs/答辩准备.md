## 一、开场白（30 秒，背下来）

> 各位老师好，我们是智能渔业-3 组。我们做的是面向珠海白蕉海鲈养殖的

## 二、项目定位与四大亮点（讲 2 分钟）

**一句话定位**：给塘主/养殖员用的「投喂决策辅助 + 执行留痕」平台，AI 只建议、人来确认、设备回执、异常可核查。

讲亮点时按这个顺序（每条 20 秒）：

1. **业务闭环完整**：不是孤立功能列表。建议→确认→下发→回执→核查是一条链，
   每一环都有状态机（画在 docs/设计说明.md），异常分支全部可演示。
2. **三个量分列**：建议量（系统算的）、确认量（人改过的）、实际量（设备实测）。
   设备没计量时实测量显示"未获取"，**绝不用确认量冒充**——这是需求书的硬约束，我们做到了。
3. **不返回伪数据**：AI 预测数据不足就明确报"数据不足"；相机离线就显示"画面不可用"，
   不拿旧截图冒充；OCR 没装依赖就明确说。这是我们把"诚实"做成了产品原则。
4. **质量有据可查**：接受过一轮第三方测试检查，6 个 P1 级问题（含越权、并发编号冲突）
   全部修复，并把每个复现场景变成了自动化回归测试，现在 **27 项验收场景全部通过**。

## 四、架构（回答"怎么实现的"用 30 秒说清）

```
浏览器/手机/小程序 ──HTTP──► Flask(API 层) ──► 服务层 ──► SQLAlchemy ──► SQLite（可切 MySQL）
  零外部依赖                    ponds/env/feeding/   suggestion/            21 张业务表
  纯 SVG 图表                   monitor/ops/          task_service/
  getUserMedia 拍照             model/community       ml / vision / environment
       ▲                                                      ▲
       └──────────── 终端仿真器 simulator/terminal.py ────────┘（HTTP 轮询回执）
```

- 三层职责：API 只管鉴权与参数，业务规则全在服务层（状态机、口径、校验），模型层 21 张表。
- 生产化：默认 waitress 多线程服务器（不是 Flask debug）；
  性能实测：批量采样 114 条/秒，5 个常用查询 p95 ≤ 31ms。

## 五、高频问答 Q&A（老师大概率问的）

**Q1：建议量是怎么算的？口径是什么？**
> 全塘单次口径：生物量(kg)=鱼重(g)×尾数/1000，乘基础比例 0.015、温度系数（适温 24-28℃ 之外衰减）、摄食状态系数，最后受单次上下限约束。每条建议把输入快照、系数、规则版本全部存库，页面上能看到完整推理链。

**Q2：AI 模型是真模型吗？准确率如何？**
> 是真训练的线性模型，不是写死的数：生长=称重记录对投后天数回归，投喂量=日投喂量对生物量+日均温回归，水质=近 72 小时趋势外推。输出都带 R²、MAE、样本数和版本号，且明确外推边界（生长≤180 天、水质≤24 小时）。我们不做黑盒大模型，因为养殖场景**可解释比准确率更重要**——老师能看懂每一步怎么算的。

**Q3：怎么防止重复投喂/重复提交？**
> 两层：客户端请求编号做幂等，重复提交返回原任务；回执按任务号去重，不重复累计用料。此外设备占用机制——设备有未结束或待核查任务时拒绝新任务。

**Q4：任务超时了怎么办？会不会自动重发？**
> 不会自动重发，这是需求书的保守要求。超时转"结果未知（待核查）"，设备保持占用；只有有权核查的人登记结论、设备满足恢复条件才解锁。我们实测过两个阶段：已下发未接收、已接收执行中失联，都能进待核查。

**Q5：权限怎么设计的？**
> 三级角色：塘主/管理员全权，养殖员按鱼塘授权（可控制、可核查分开授权）。所有接口做资源绑定校验——比如用 A02 的建议编号去 A01 下发任务会被拒绝，第三方测试专门验证过这类越权，已修复并有回归测试。

**Q6：并发下有没有问题？**
> 测过：8 线程 16 次并发生成建议，编号唯一冲突通过回退重试解决，16 次全部成功。这是第三方测试发现的真问题，我们修的。

**Q7：为什么用 SQLite 不用 MySQL？**
> 课程要求口径是 MySQL，我们保留了完整支持（.env 一行切换）。默认 SQLite 是为了"拷贝文件夹即可演示"，答辩和部署零配置。业务代码走 SQLAlchemy，不依赖数据库特性。

**Q8：测试怎么做的？**
> 28 个验收场景全部自动化（`tests/test_acceptance.py`），覆盖正常流程和异常分支：数据失效、重复提交、回执超时、迟到回执、乱序回执、跨塘越权、输入校验、16 并发、模型训练、视觉识别、数据导入。**默认跑在独立临时库上，不影响演示数据**。另有投喂安全回归（`tests/test_feeding_safety.py`，9 项）和性能基准（`scripts/benchmark.py`，报告在 docs/）。

**Q9：微信小程序做了什么？**
> 原生小程序脚手架：鱼塘列表/单塘看板/交流排行三页，wx.request 直连后端同一套 API。真机预览需要 AppID，所以演示以响应式 Web 为主，这是需求书 2.3 允许的。

**Q10：这个系统能真用吗？**
> 诚实回答：流程和工程是按真实业务设计的（幂等、占用、核查、审计日志），但演示规则和 AI 参数是课堂联调口径，**不能作为实际养殖依据**——界面上也一直挂着这个提示。接入真实传感器和标定过参数后才能生产使用。

## 六、数据口径速查卡（被追问时翻这页）

| 概念 | 口径 |
|---|---|
| 建议量 | 系统生成，全塘 kg，依据含输入快照与规则版本 |
| 确认量 | 人工最终下发量，改量必填原因 |
| 实际量 | 设备实测（measured）或未获取（unknown），不顶替 |
| 任务状态机 | pending→dispatched→running→done/failed/stopped；超时→unknown→核查后落定 |
| 用料统计 | 确认量累计，**只计 done/stopped**（失败、进行中不算） |
| 饲料系数 FCR | 称重区间内用料 ÷ 同区间鱼体增重，越低越好；两页面口径一致 |
| 数据来源 | real/sim/manual/csv 四种分列标识，界面可见 |
| 排名规则 | FCR 升序；称重不足的塘"未参与"，不凑名次 |

## 七、限制的"诚实话术"（被挑战时用）

- 被问"视觉识别准不准"：算法是 OpenCV 启发式（亮残差+连通域），会误报反光和水草，所以产品设计上识别结果**永远是待确认事件**——这是故意的安全设计，不是没做完。
- 被问"OCR 呢"：接口已实现，需要本机装 tesseract；没装时明确提示，不返回假文字。
- 被问"真实硬件"：终端是仿真器，但协议就是 HTTP 轮询+回执，真设备接入只需实现同样接口。
