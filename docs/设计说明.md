# 白蕉水产养殖管理平台 · 设计说明

对应《白蕉水产养殖管理平台需求说明书》（组员 V1.2）的实现说明。

---

## 1. 分层与模块对应

| 需求书模块 | 实现位置 | 说明 |
|---|---|---|
| 采集控制终端 | `simulator/terminal.py` | 注册、心跳、周期采集、任务去重、回执、故障注入 |
| 后端系统 | `backend/api/*`、`backend/services/*` | 校验、建议、任务、核查、事件、日志、权限 |
| 数据库与模型模块 | `backend/models.py`、`scripts/` | 业务记录持久化；模型模块按 2.3 列为后续扩展 |
| Web 前端看板 | `backend/templates/index.html`、`pond.html`、`compare.html` | 单塘、多塘、投喂确认、运营与日志入口 |
| 移动端 | 同一套响应式页面（`static/css/style.css`） | 小程序按 2.3 列为后续扩展 |
| 视觉与光学模块 | `api/monitor.py`（`vision/detect`） | 仿真识别，来源标 `sim`，需人工确认 |

后端不直接操作现场硬件，前端不直接访问数据库或设备——与需求书 2.2 一致。

## 2. 数据模型要点

`models.py` 按需求书 7.1「主要业务记录」设计，关键约束：

- `FeedingTask`：`suggested_amount / confirm_amount / actual_amount` 三列分列，
  `actual_source ∈ {measured, manual, unknown}`；`request_no` 唯一（幂等键），
  `task_no` 唯一（下发主键），`device_locked` 表示设备占用。
- `Receipt`：`late`（迟到回执）、`duplicate`（重复回执）、`seq`（序号）用于去重与追溯。
- `Review`：核查结论、依据、设备恢复依据；`conflict` 标记与迟到回执的冲突。
- `Measurement`：`collected_at`（采集时间）与 `received_at`（接收时间）分开，
  支持断线补传；`valid / invalid_reason` 保留异常标记。
- `Alert`：`is_ongoing / occurrence_count` 支持「持续事件」，避免重复刷新产生大量记录。
- `AuditLog`：覆盖 `validate / task / control / config` 四类，不含明文密码。

## 3. 关键业务规则实现

### 3.1 建议生成（`services/suggestion.py`）

流程严格按需求书 5.3：

1. **先判温度有效性**（是否存在、是否过期）→ 无效直接返回原因，不计算；
2. 取**日内统计特征**（`environment.day_features`），不使用即时值代替全天变化，
   缺测不补零；
3. 按 `rule_version` 规则计算，保存**输入快照**（`inputs_json`）与**依据**（`reason`）；
4. 失败返回明确原因，**不以 0 投喂量冒充失败结果**；
5. 课堂规则标注「演示规则（测试用途，非养殖依据）」。

### 3.2 任务与幂等（`services/task_service.py`）

- 相同 `request_no` → 返回原任务（`reason=duplicate`）；
- 校验建议是否过期、确认量是否在允许范围、修改建议量是否填写原因；
- **设备占用检查**：同一 `device_id` 已有 `device_locked=True` 的任务则拒绝；
- 先持久化任务与设备占用，再由调用方 `dispatch` 下发。

### 3.3 回执与异常

| 情形 | 实现 |
|---|---|
| 重复回执 | 同 `kind` 已存在 → 标记 `duplicate`，不推进状态、不累计用料 |
| 迟到回执 | 任务已核查结束 → 标记 `late`；结论冲突则置 `Review.conflict` 并告警 |
| 回执超时 | `check_timeouts` 将超时任务转 `unknown`、保留占用、产生告警 |
| 卡料 | `finish(failed)` + `fault` → `failed`，生成 `feed_fail` 告警，保留已知实际量 |
| 实际量未知 | `actual_amount=None, actual_source='unknown'`，**不用确认量补齐** |
| 停止 | 收到 `stop` 回执才置 `stopped`；设备不支持远程停止时保留已知信息 |

### 3.4 核查（`services/task_service.review`）

结论 `done / stopped / failed / not_executed / unknown`；结论为 `unknown` 时保持待核查；
必须填写核查依据；正在下发/执行的任务不可直接核查结束。只有登记**设备恢复依据**并逐项确认终端无任务执行、旧指令不会继续执行、设备可用后，才解除设备占用（`device_locked=False`）。

### 3.5 权限（`services/common.py`）

角色 `owner / admin / operator`；`PondGrant` 控制养殖员可访问与可控制的鱼塘。
无控制权限者提交任务由**后端**拒绝（返回 403），不依赖前端隐藏按钮。但身份来源仍是客户端指定用户名，只能作为角色权限演示，尚未实现真实用户和设备认证。

## 6. 扩展项实现与剩余限制（对应需求书 2.3）

原列为「后续扩展」的能力本轮已实现（可解释、不伪结果）：

- **AI 模型预测**：`services/ml.py` 纯标准库线性回归（正规方程 + 高斯消元），
  `api/model.py` 提供 train / status / predict 三个接口。
  - 生长：体重(g) ~ 投后天数；输出日增重、达标天数与预计日期（外推 ≤180 天）。
  - 投喂量：日投喂量(kg) ~ 生物量(kg) + 日均水温(℃)；预测按近 3 天水温折算。
  - 水质：最近 72 小时小时均值线性趋势，外推 ≤24 小时。
  - 模型落盘 `data/models/*.json`，带版本、样本数、R²/MAE、训练时间与口径说明。
  - 数据不足 / 未训练返回 `reason=insufficient_data / model_not_trained`，不返回伪预测。
- **视觉识别**：`services/vision.py`
  - 帧分析 `cv-float-v1`（OpenCV）：大核背景估计 → 亮残差 → 连通域过滤，
    附画面亮度/模糊质量检查；检出生成待确认事件（source=vision），人工确认前不计数。
  - 接入方式：浏览器摄像头拍照 / 图片上传 → `POST /api/ponds/<id>/vision/frame`；
    相机通道状态随帧上传转在线。
  - OCR：`POST /vision/ocr`，依赖 tesseract-ocr；未安装返回 `ocr_unavailable`，不做假识别。
- **交流与排行榜**（5.11）：`api/community.py`
  - 交流帖：发布 / 回复 / 关闭，分类（经验交流/问题求助/行情信息）。
  - 排行榜：窗口期内 FCR（饲料消耗/鱼体增重）升序排名，附口径说明；
    称重或数据不足的塘标注「未参与排名」及原因，不凑名次。
- **微信小程序**：`miniprogram/` 原生脚手架（鱼塘列表/单塘看板/交流排行三页），
  `wx.request` 直连后端；需开发者工具导入并配置 BASE_URL。

仍未实现：

- **真实硬件接入**：本机无传感器 / 相机 / 投料机；相机以浏览器摄像头与图片上传代接入。
- **深度学习视觉模型**：当前为启发式算法，误报可能（反光/水草/水花），结果需人工确认。

## 8. 演示开关：终端仿真器

页面右上角「终端仿真」开关（`/api/simulator/start|stop|status`），
后端内启动/停止仿真终端，用于一键对比两种情形：

| 开关 | 效果 | 对应验收场景 |
|---|---|---|
| **开** | 仿真终端自动应答 accept/execute/finish，投喂任务数秒内跑完闭环，设备自动释放 | 正常投喂、重复提交 |
| **关** | 下发后无终端应答 → 停在「已下发待回执」→ 超时巡检转「结果未知（待核查）」→ 暂停下发，须人工核查才释放 | 回执超时、核查与恢复 |

**实现**：`services/simulator_ctl.py` 在后台线程运行 `simulator/terminal.py` 的
`Terminal` 类（已改为可传入 `base` 地址，供进程内回调）；waitress 多线程保证
仿真终端回调自身服务时不阻塞。

**诚实性约定（需求书 5.3）**：仿真终端回执声明 `source=simulated`，后端据此把
`actual_source` 标为 `simulated` 而非 `measured`，界面与统计不得当作实测数据
（「汇总不得伪装成实测值」）。

**边界**：仿真终端不投任何真实饲料，不连接真实硬件；仅用于课堂联调与演示。

## 9. 投喂回归补充

- 仿真终端使用持久化任务日志（`simulator/task_journal.py`，落盘
  `data/terminal-state/`），先认领再执行；完成结果先落盘再发送。
  重启只补发结果，不重放投料。认领后中断且无完成结果的任务留待核查。
  该目录需跨重启保留，任务未核实前不要删除；升级仿真器前应先结束/核实旧任务，
  新日志无法恢复旧版本未记录的执行历史。
- Web/小程序可以请求停止（`POST /api/tasks/<task_no>/stop`），经控制权限校验后
  以审计记录持久化，终端轮询读取 `stop_requested`；收到停止回执前不释放占用，
  不支持停止或无回执时仍需现场处理。
- 实际用料由 `services/feed_statistics.py` 统一汇总，失败前已知投料也计入；
  未确定量导致 FCR 暂不能计算，不以确认量代替。界面新增 `actual_feed_kg`，
  `confirmed_feed_kg` 保留确认量原义。
- 核查页显示原回执和历史核查，须填写真实依据，不再自动生成「现场取证」；
  解除占用要求 `recovery_checks` 三项独立布尔确认
  （`terminal_idle` / `old_command_disabled` / `device_ready`），
  这些是管理员的现场核实记录，不是系统自动证明设备安全。
- 验证：`python tests/test_feeding_safety.py`；原验收脚本
  `python tests/test_acceptance.py` 仍单独运行。
  真实身份认证与模型独立测试未纳入此次修复，见 README 已知限制。
