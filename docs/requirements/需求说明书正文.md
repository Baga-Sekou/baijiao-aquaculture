# 白蕉水产养殖管理平台需求说明书

## 1 项目背景

### 1.1 课题背景

本项目围绕珠海斗门白蕉的水产养殖场景，设计一套供养殖户日常看塘、投喂和处理异常的平台。课程关注的是养殖户如何兼顾鱼的生长、饲料投入和养殖质量。作出这些判断需要参考养殖记录和设备信息，但现有信息难以直接满足这一需要。[1][2]

课堂案例提到了过量投喂、饲料未被充分摄食、水质变差，以及鱼的健康、死鱼和减产风险。因此，平台首先围绕合理投喂和鱼塘监控展开设计。养殖户需要查清当前鱼塘的情况，核对每次准备投喂的数量，并了解设备的实际执行结果；出现异常时，也应有相应的查看和处理入口。课堂讨论的脂肪肝和品质问题作为项目背景保留，疾病诊断与治疗不属于系统职责。

### 1.2 需要解决的问题

养殖户按固定时间、固定投喂量或现场经验投喂时，往往难以同时对照温度、溶氧、鱼的生长阶段和最近的投喂情况。投喂决策缺少完整记录，发生饲料浪费后便难以查清当时的判断依据。

水质数据、相机画面、设备状态和投喂记录分散在不同位置，养殖户需要反复查看，离开鱼塘后更难及时了解变化。数据缺少更新时间，或设备已经离线，都可能让旧数据被误认为当前状态。

设备断线、卡料或回执超时后，实际投喂结果可能与下发的指令不一致。此时，即使页面提示操作成功，也无法据此确认饲料已经投出。只记录指令下发会使实际用料难以准确统计，养殖户重复操作时还可能再次投料。

### 1.3 建设目标

平台应集中展示鱼塘环境、监控画面和设备状态，提供有数据依据的投喂建议，并记录从人员确认、任务下发到设备反馈的过程。出现数据异常、设备故障或疑似死鱼时，应保留异常发生的时间、对象和处理结果，方便养殖户核查。

实训阶段以业务流程能够完整运行、记录能够追溯和异常分支能够演示为目标。节省饲料和改善养殖结果是后续应用需要评价的效果，应结合真实养殖周期、生长情况和成本记录验证，不以模拟数据的结果代替现场效果。

## 2 产品概述

### 2.1 产品定位

白蕉水产养殖管理平台供养殖户及日常管理人员使用。电脑看板用于查看鱼塘整体情况，小程序便于在现场或外出时查看状态、确认投喂和处理异常。业务处理和记录管理由后端完成，鱼塘边的采集控制终端连接传感器、相机和投料设备。[2]

本平台围绕养殖过程开展管理。鱼类收购分选、商品交易、物流和面向消费者的品质认证不纳入本期范围。

### 2.2 系统组成

| 组成部分 | 主要职责 |
|---|---|
| Web 前端看板 | 单塘监控、多塘比较、养殖计划、投喂和运营记录，展示在线人数及日志 |
| 小程序端 | 提供移动查看、投喂确认、任务查询和异常处理入口 |
| 后端系统 | 接收终端注册与数据，组织查询、模型调用和控制指令，管理权限及日志 |
| 采集控制终端 | 读取设备数据，上传状态，接收并执行控制任务，返回处理结果 |
| 硬件设备 | 水质及摄食传感器提供测量，水上和水下相机采集图像，投料机执行投喂 |
| 视觉与光学模块 | 确定成像条件，提供画面及约定的识别结果和输出协议 |
| 数据库与模型模块 | 保存基础和动态数据，完成清洗、特征整理、训练测试及预测服务 |

系统按“鱼塘硬件—采集控制终端—后端—Web 与小程序”连接。视觉处理和数据模型各自提供明确的输入、输出，由后端组织调用。后端不直接代替采集终端操作现场硬件，前端也不直接访问设备或数据库。上述拆分对应课程中的硬件、视觉光学、采集、后端、Web、小程序和数据库分工。[1][6]

### 2.3 本期方案与边界

本期按“系统提供建议、养殖员确认后执行”设计投喂流程，分别保存建议量、确认量和实际量。养殖员调整数量时填写原因。按计划无人确认投喂、摄食反馈自动联动及自动停止列为后续扩展。

本期需求设计覆盖单塘与多塘管理、环境和摄食数据、投喂建议及控制、视频与疑似死鱼事件、养殖计划、称重与用药、成本记录、告警统计、三级权限，以及数据处理和模型服务。第5章说明各模块功能，第9章给出检查场景。交流与排行榜单独列为扩展，不作为本期基础功能验收项。

模型部分设计投喂量、生长和水质三类预测的独立输入输出，并要求具备数据的模型完成训练与测试。数据尚不满足条件的目标保留接口和缺失条件说明，验收时标记为接口演示或尚未完成模型测试。视觉部分分别检查画面接入、识别接口和识别效果；人工登记用于现场核查。各项实际完成程度应据测试证据填写。

实训可使用仿真设备验证相同的任务与反馈流程，界面和记录须标明来源；实物接入另按实际设备进行验证。课程历史 CSV 用于历史查询和训练流程演示，日内曲线、故障及执行回执另行准备。本说明书是拟定的课程设计，设备条件、数据定义和算法效果目标等实施依赖集中列于第10章。

### 2.4 技术分析

采集系统需要处理串口或网口设备，解决连接、采样、解析、本地保存和上传问题。后端需要维护多个终端的连接及归属，完成并发接收、数据整理、持久化、模型调用和业务接口。Web 与小程序共享后端数据，在不同屏幕上提供相应的查看和操作方式。[1][3]

课堂课件以 Python 和 Flask 介绍采集与后端开发，前端示例展示了动态页面及图表。需求层面要求各端能够按协议协作，不将示例中的框架版本、接口路径或端口直接作为固定协议。后端框架应在实施前结合课堂最终说明确定。

环境预测、生长预测和投喂量预测分别定义预测对象、时间范围、输入特征和输出单位。模型处理流程与效果测试按第5.10节验证，相机成像与识别按第5.5节分别验证。

## 3 用户说明

### 3.1 目标用户

| 用户角色 | 主要使用场景 | 操作范围 |
|---|---|---|
| 塘主 | 掌握全部所属鱼塘的养殖、用料和经营情况 | 管理所属鱼塘及管理员，查看汇总和经营记录 |
| 管理员 | 安排人员、养殖计划、日常任务和异常处理 | 在授权鱼塘内维护资料，分配运营者及操作权限 |
| 运营者（养殖员） | 看塘、投喂、称重、用药登记和现场处理 | 查看被分配鱼塘，执行授权任务，填写现场记录 |

三级角色沿用课件中的塘主、管理员和运营者划分；具体权限为本项目拟定方案。同一人员可以兼任角色，个人养殖户可以自行管理所属鱼塘。查看、投喂控制、设备维护和投喂核查分别授权；核查结论由具备该权限的管理员确认，养殖员可提交现场证据。[7]

### 3.2 典型使用过程

早晨准备投喂时，养殖员先在小程序中选择鱼塘，查看环境数据的更新时间、近期趋势、设备状态和本日已完成的投喂记录。系统根据有效数据生成建议后，养殖员核对投喂对象和数量，确认或修改建议，再提交任务。任务结束后，养殖员查看实际执行结果；有异常时到现场核查。

养殖户不在鱼塘时，可通过看板或小程序查看监控画面和最新记录。若画面中发现疑似死鱼，可登记位置、时间和图片，由现场人员确认。相机离线时，页面应明确提示画面不可用，不能继续以旧截图表示正常监控。

维护人员处理设备故障时，需要知道哪个塘、哪台设备、何时开始异常以及当时的任务状态。处理完成后补充原因与结果，系统保留故障前后的记录，便于判断是否需要补采数据或人工核实投喂量。

### 3.3 主要使用要求

界面应使用养殖员容易理解的名称，同时显示数据单位和时间。投喂操作需要集中呈现鱼塘、设备、数量和单位，避免在多塘切换时误操作。错误提示应说明当前不能操作的原因及后续处理入口，而不是只显示错误代码。

## 4 项目价值

### 4.1 用户价值

看塘、数据查询、投喂和异常处理记录都按鱼塘归集，养殖员可以少花时间查找信息。养殖户查看投喂记录时，能够对照建议量与实际用料，查明决策依据；回顾异常时，也能找到当时的数据和设备反馈。

### 4.2 经营与应用价值

环境、投喂和异常记录积累后，可用于比较不同养殖批次、检查用料变化，为调整投喂办法提供参考。经营效果还要结合鱼的生长、养殖周期、饲料支出和销售结果评价，仅凭投料减少无法判断效益是否提高。

开发和维护人员可根据设备接口、任务记录及异常信息定位现场问题，后续接入其他鱼塘也有据可循。推广应用前，仍需验证平台能否适应不同设备、鱼种和养殖条件。

## 5 功能模块需求

### 5.1 鱼塘与养殖批次管理

系统应维护鱼塘编号、名称、规模、负责人及关联设备。鱼塘编号应能够唯一识别管理对象。面积等带量纲的信息必须同时保存单位，已经产生记录的鱼塘不应直接删除其历史数据。

同一鱼塘可按养殖周期建立批次，记录鱼种、种苗来源、投放日期、鱼数量、初始鱼重、目标鱼重、称重周期和预计上市日期。养殖计划与实际称重、投喂记录关联，显示当前阶段及计划进展；预计日期与实际完成日期分别保存。[7]

调整鱼数量或鱼重时保留更新时间与填写来源。不同批次分别查询统计，避免将重新投苗后的数据接在上一批鱼的生长曲线上。原始资料未提供批次标识时，应先确认归属再关联。

### 5.2 环境数据采集与查询

采集终端应按配置周期读取水温、溶氧、pH、ORP 等已接入指标。每次上传应带鱼塘、设备、采集时间、指标值、单位及采集状态。后端检查必填字段、数据类型、时间和设备归属，保存校验结果。盐度等其他指标按实际设备能力扩展。[3]

看板和小程序应显示最近一次有效测量及其时间，并可按鱼塘和日期范围查看趋势。缺测区间应以空缺或明确标记表示，不用零值代替；超出有效期限的数据应显示已过期。指标有效范围、采样周期和过期时间由配置给出，配置变更应可追溯。

发现超量程、疑似漂移或传感器离线时，系统应保留原始记录和异常标记，将无效数据排除在投喂建议输入之外。单个设备异常不应阻塞其他设备的数据接收。终端与后端通信中断时保留可用的本地待上传记录，恢复后补传，并区分采集时间与补传时间。

摄食传感器、视觉服务或现场观察提供的摄食状态，应记录来源、时间、状态含义及有效性。原始摄食信号、算法得到的饥饿度和人工判断分别保存；接口未约定前，不将活跃度数值直接解释成“还需要多少饲料”。

后端应保留一天内的原始测量曲线，并在剔除无效样本后生成所需的统计特征。每项统计注明时间窗口、有效样本数、缺测情况和处理方法；按模型需要提供最低值、最高值、均值或变化特征。不能把缺测补成零后求平均，也不能用当前温度代替全天温度变化。传感器采样深度和位置能够取得时一并记录，避免混淆不同测点。[3]

### 5.3 投喂建议

系统应结合鱼塘与批次信息、鱼数量及生长阶段、经过清洗的环境曲线或统计特征、有效摄食状态和历史投喂记录生成建议。输入项由所选规则或模型定义，不要求每个模型都使用全部字段。建议应包含适用鱼塘、生成时间、投喂量及单位、有效期限，以及所用数据和规则或模型版本。前端应能说明主要依据，例如温度统计覆盖哪个时段、数据是否完整、采用哪一版规则，而不是只展示一个数量。[2][4]

温度参与决策的过程应可追溯。系统先判断温度数据是否有效，再按选定规则或模型计算建议；温度变化后重新计算应形成新建议，不直接修改已经提交或执行中的任务。具体温度与投喂量的关系由业务规则定义，本说明书不预设养殖阈值。

缺少必需输入、数据过期或计算失败时，系统返回无有效建议及具体原因，将失败状态与有效的数量结果区分。建议应由本次有效输入计算得到，课堂联调用的示例规则须明确标识其测试用途。

### 5.4 投喂控制与执行记录

养殖员确认建议时，系统应检查其鱼塘权限、设备状态及建议是否仍有效，并显示本次确认量。修改数量必须大于零，使用已定义的单位，且满足配置的操作限制。系统保存原建议和修改原因，形成可追溯的确认记录。

终端接入时应向后端登记身份、关联鱼塘及设备，后端校验后记录连接状态。重复连接、断线和重新连接应更新同一终端状态，不能产生错误的鱼塘归属。后端应能查询已连接终端数量；终端连接数与在线用户数分别统计。[3]

客户端为一次确认生成请求编号，网络重试沿用同一编号。后端校验通过后生成唯一任务编号，保存任务及设备占用，再下发至对应终端；相同请求返回原任务，两端可凭请求编号找回提交结果。终端按任务编号去重，重连或重启后仍能识别已接收任务。终端返回已接收、执行中、已完成或失败等状态，页面据反馈更新。同一设备已有未结束或待核查任务时，暂不接受新的投喂任务。

任务至少记录建议量、确认量、实际量、提交人、提交时间、执行起止时间和结果。设备只能报告完成状态而不能测量实际量时，实际量显示未获取；需要人工补录时记录补录人和依据，不能把确认量当成实测量。

养殖员应能够请求停止正在执行的任务。系统收到设备停止反馈后记录已停止及已知投料情况；设备不支持远程停止或反馈超时时，页面提示需要现场处理。卡料、失联等故障产生异常记录，执行结果不明的任务先进入待核查状态，核实前不自动重新下发投料。

待核查任务由授权管理员处理。核查页面应汇集原任务、已收回执和故障记录，支持查询终端执行记录及登记现场证据。管理员填写核查时间、依据和结论，将原任务确认为已完成、已停止、失败或未执行；仍无法判明执行情况时保持待核查。实际量无法确定时保留未获取，核查结论与实测量分别记录。

关闭核查后，还须确认终端已无该任务在执行、旧指令不会继续执行且设备可用，才解除设备占用。判为未执行的任务保留原记录；需要重新投喂时重新取得有效建议并由养殖员确认，创建新任务。迟到或重复回执关联原任务保存，不重复累计用料；与核查结论冲突时提示再次核对，保留双方证据及修订记录。

### 5.5 视觉光学与死鱼监控

视觉光学模块应明确水上、水下观察位置、视野、光照、图像质量和采集方式，并将相机编号与鱼塘关联。镜头、光源和工作距离应根据实际观察条件，通过现场或样例成像验证。[1][8]

平台应按鱼塘展示已接入相机的画面或最近图像，标明相机、获取时间和在线状态。用户能够从鱼塘页面进入对应监控入口；画面加载失败时给出提示，不影响环境数据及历史记录查询。[2]

养殖员发现疑似死鱼时，可提交事件，记录鱼塘、发现时间、位置描述、观察情况和图片。识别服务应输出疑似对象、图像或视频定位信息、采集时间、模型版本，以及能够提供的置信度。服务产生的结果作为待确认事件展示，并保留识别来源。识别失败和未检测到疑似对象应分别表示。人工确认前不得将疑似结果直接计入已确认死鱼数量。

事件处理过程包括待确认、处理中和已处理；误报可标记为误报并保留说明。确认人员填写确认结果，处理人员登记现场处置情况。确认死鱼事件本身不等于确定病因，页面不据此生成诊断结论。

### 5.6 异常与日志管理

系统应汇集环境数据异常、设备离线、投喂失败和疑似死鱼事件，记录对象、发生时间、异常类型、当前状态和处理信息。看板和小程序提供待处理列表；同一设备持续异常时关联为持续事件，避免重复刷新产生大量独立记录。

处理人员可登记已查看、处理过程和处理结果。异常事件关联原投喂任务，提供第5.4节的核查入口。设备恢复在线、事件处理完成、任务核查结束和设备可接受新任务分别记录，关闭一般告警不能直接解除投喂任务占用。[3]

日志应覆盖数据校验失败、任务下发与反馈、控制操作和参数变更。查询时可以按鱼塘、设备、任务编号或时间检索。日志用于定位问题，不记录明文密码等认证信息。

### 5.7 Web 看板与多塘比较

Web 页面保持主要导航及底部入口稳定，点击导航时切换中间内容区域，并保留当前鱼塘和筛选条件。单塘首页呈现鱼塘状态、养殖计划进度、水上及水下监控、当日投喂和待处理事项。页面提供在线人数与运行日志入口，在线人数的统计周期和去重规则由后端统一定义。[6][7]

图表应覆盖鱼数量变化、温度、溶氧、pH、ORP、饲料用量、告警和用药记录。用户可按鱼塘和时间段筛选，查看数据点的时间、数值、单位与来源。当天水质采用实际采样时间展示；按日、周、月汇总时明确统计口径。相机、ORP 等尚未接入的项目显示未接入，不填入看似真实的示例值。

多塘汇总提供列表、参数排序和进入单塘的入口。同一时间范围内可对照多个鱼塘的水质、告警频率、用药频率、饲料用量和饲料系数。比较时标明鱼塘规模、鱼种、养殖阶段与样本覆盖情况；数据条件不同的鱼塘不能直接据此判定优劣。

饲料统计区分当日、所选时段平均和累计用量。饲料系数必须使用已约定的饲料消耗与鱼体增重口径，缺少有效增重数据时显示暂不能计算。节省饲料量需要有同口径的基准记录；没有基准时不展示“已节省”的累计数字。支持导出当前授权范围和筛选条件下的记录，导出内容包含时间、单位及来源。

### 5.8 小程序

小程序通过同一后端提供鱼塘选择、单塘状态、历史趋势、监控入口、投喂确认、任务查询及现场记录。移动端优先展示当前对象、关键异常和需要完成的任务；复杂的多塘分析在 Web 中展开，小程序仍应能切换所属鱼塘。[7][9]

两端使用同一权限、建议和任务记录。网络异常时区分未提交、提交中和结果未知，恢复连接后查询原任务。投喂操作再次进入页面时应显示实际状态，避免因界面无响应重复投喂。小程序的页面布局和触控操作需在开发者工具及实际手机上验证。

### 5.9 养殖运营与用药记录

管理员可按鱼塘安排每日、每周任务，记录任务内容、执行人、计划时间、截止时间和完成情况。养殖员填写投喂、称重、巡塘及用药等实际记录，未完成和逾期任务保留提醒；手动标记完成不能替代投料机的执行回执。[7]

用药记录包括鱼塘、时间、用品名称、数量和单位、操作人及备注，可按日、周、月查看次数变化并进行多塘比较。该功能保存实际操作记录，不自动生成诊断或用药剂量。高频记录作为回顾管理情况的线索，不能单凭次数认定水质问题或疾病。

平台记录饲料品牌、用量、单价及其他已知养殖投入，区分预计成本、实际支出和预计产出。需要评价本轮效益时，应有相应出塘与销售记录；缺少记录的指标显示未获取，不能依据模拟曲线填出真实利润。

### 5.10 数据处理与模型预测

数据模块应提供“导入与校验—清洗—特征整理—训练及测试—部署调用”的处理过程，保存所用数据范围和版本。清洗结果与原始数据分开，记录剔除或修正原因。相关性分析用于辅助选择特征，不能只按相关系数高低删去具有业务意义的变量。[4]

投喂量预测、鱼类生长预测及水质预测分别管理。每个模型注明目标变量、输入字段和单位、预测时间范围、适用场景及测试结果；以历史投喂记录为标签训练的模型只能说明对该记录的拟合能力。生长或水质预测须具备相应的目标数据，不以投喂量模型替代。

训练与测试按时间或批次划分，记录各自日期范围、样本数和划分方法。清洗及特征处理中的拟合参数只从训练数据取得，预测输入仅使用预测时已经能够获得的信息。参数选择在训练阶段完成，最终测试集用于独立评价。

每个完成训练的模型应提供可复现的测试记录：数据与模型版本、预测目标和时间范围、样本划分、处理方法、预测结果、失败样本，以及适合该目标的误差指标。数量预测可采用平均绝对误差等指标，并注明单位；同时与预先选定的简单基准在同一测试集上比较，例如对适用的连续测量预测使用上一时刻值。基准及指标须在测试前确定。

训练流程验收检查上述证据是否完整、划分是否合理、结果是否可复现；预测效果是否达标则按事先约定的目标判断，未设定目标时仅报告误差和基准比较。接口联调成功、训练流程通过和预测效果达标分别记录。课堂模拟数据上的测试结果只反映该数据集的表现。

后端通过约定接口调用模型，传入满足要求的特征，取得结果、单位、版本和处理状态，并将预测曲线与实测曲线区别展示。训练任务应与正常采集、控制独立运行。模型未配置和计算失败分别返回明确状态及原因。

### 5.11 信息交流与排名

课件展示了养殖交流、经验分享和排行榜，列为后续扩展。启用时需提供信息发布、查看和必要的内容管理，并确定排名指标、比较范围和数据来源。公开生产记录须取得对应养殖户授权。[7]

## 6 主要业务流程

### 6.1 温度影响投喂建议

温度传感器产生测量值后，由采集控制终端连同设备与时间信息上传。后端校验并保存记录，前端显示最近有效温度及趋势。数据模块先整理所需时段的温度曲线，标记异常和缺测，生成规则或模型要求的特征。规则服务读取这些特征和其他必要信息，保存计算依据，并将建议提供给看板及小程序。

养殖员查看新建议后决定是否确认。若温度数据无效或所需时间窗口的数据不完整且不满足模型输入要求，系统停止此次建议计算并显示原因；若已经有任务在执行，后到的温度数据只用于展示及后续建议，不擅自改变当前任务。实际需要中止投喂时，按停止任务流程处理。

### 6.2 喂养指令传递

| 步骤 | 参与方 | 处理与结果 |
|---|---|---|
| 1 | 养殖员与看板或小程序 | 选择鱼塘，核对有效建议，确认投喂数量 |
| 2 | 后端 | 校验权限、设备与建议；按请求编号去重，保存任务和设备占用后返回任务编号 |
| 3 | 后端与采集控制终端 | 下发任务；终端核对目标设备和重复任务，返回接收结果 |
| 4 | 采集控制终端与投料机 | 执行投料，反馈进度及设备状态 |
| 5 | 终端与后端 | 返回完成、停止或失败结果，以及可取得的实际投喂量 |
| 6 | 看板与小程序 | 查询并显示同一任务结果，异常时提供现场核查入口 |

请求被拒绝时返回原因。执行阶段反馈超时，原任务进入待核查并继续占用设备；按第5.4节核实执行结果和设备状态后结束核查。上述步骤和温度数据流程共同构成模块时序图的主要内容。

### 6.3 死鱼事件处理

人工观察或识别接口产生疑似事件后，系统关联鱼塘和图像并展示待确认状态。养殖员查看画面或到现场核查，填写确认结果；确有异常时登记处理过程和结果，误报则保留误报说明。系统将事件与同期环境及投喂记录关联查询，便于回顾现场情况。

## 7 数据与接口要求

### 7.1 主要业务记录

| 记录类别 | 必须能够追溯的信息 |
|---|---|
| 鱼塘与批次 | 鱼塘编号、批次、负责人、规模及单位、开始时间和资料来源 |
| 环境测量 | 鱼塘、设备、采集时间、接收时间、指标、值、单位及有效状态 |
| 投喂建议 | 建议编号、适用鱼塘、输入记录、规则版本、建议量、单位及有效期限 |
| 投喂任务 | 请求与任务编号、建议关联、确认量、实际量及来源、操作者、阶段状态和设备占用 |
| 异常与监控事件 | 事件编号、鱼塘或设备、时间、证据、确认人和处理记录 |
| 投喂核查 | 原任务、核查人和时间、回执与现场依据、结论、设备恢复依据及修订记录 |
| 计划与运营记录 | 养殖目标、计划日期、任务执行人、称重及用药记录、实际完成情况 |
| 模型与预测 | 数据版本、特征定义、预测对象及时间范围、测试记录、模型版本和结果 |
| 成本及比较统计 | 实际用料和支出、统计区间、基准记录、增重来源及计算口径 |

设备、建议、任务和事件应使用可关联的编号。接口至少覆盖终端注册与连接状态、环境及摄食数据上传、图像与识别结果、历史查询、模型请求、投喂下发与回执、运营登记和权限校验。每类接口需明确发送方、接收方、触发条件、字段类型、单位、成功响应和错误响应；控制接口还应规定超时、重复请求与迟到回执的处理。具体路径和通信格式在接口设计中给出。[2][3]

### 7.2 课程测试数据

课程提供的压缩包包含 2024 年和 2025 年两份模拟 CSV，分别有 366 条和 365 条记录，全部属于 A01 鱼塘。字段涉及日期、时刻、鱼塘规模、鱼数量、温度、溶氧、盐度、pH、水质指标、鱼重、活跃度、投喂间隔和投喂重量。[5]

导入时应保留原字段及文件来源，使用独立记录编号，避免两年重复的 id 相互覆盖。同一来源文件和源记录编号重复出现时不重复写入；内容不一致时报告冲突。由于跨年鱼重发生重置，批次归属需确认后再进行连续生长分析。温度、盐度、鱼重和投喂量等字段必须明确单位及统计口径后才能参与业务计算。

这批数据每天一条，可用于历史查询和训练流程演示，不能恢复一天内的传感器变化，也不提供视频、死鱼标签或设备回执。实时采集与故障演示需另外准备标明来源的测试输入。模型训练如以历史投喂量为目标，应说明其含义是拟合记录中的数量，而非已经得到最佳投喂量。

## 8 非功能需求

### 8.1 操作与权限

系统应在服务端校验鱼塘访问和控制权限。无投喂权限的用户不能通过页面或直接调用接口发起任务。控制操作和参数修改记录操作人；需要再次确认的操作应显示明确对象，不能只用颜色区分状态。

### 8.2 可靠性与数据一致性

通信故障应能够被观察和记录，单个设备故障不影响其他正常设备。补传数据、重复操作和重复回执应保持记录一致，不重复形成实际投喂。环境、任务及事件记录应有持久化存储，程序重启后仍可查询已保存的记录。

### 8.3 配置与维护

采样周期、数据有效期限、设备量程、任务超时和规则版本应统一配置。配置修改保留生效时间和操作者，使历史记录仍能解释当时的行为。部署说明应包括启动、连接设备、查看日志和恢复数据的方法。

### 8.4 性能与界面响应

页面应及时反馈加载、提交与执行状态，耗时操作不能导致重复提交。测试时记录端数、设备数、采样频率及查询时间范围，再评价接收与查询能力。具体响应时间和并发目标在设备及部署条件确定后约定，不以未经测试的数字作为已实现能力。

## 9 验收要求

系统验收以完整业务场景为单位，并核对硬件、视觉、采集、后端、数据库与模型、Web、小程序各模块的接口责任。正常流程检查输入、决策、执行和记录是否对应；异常流程检查错误是否明确、数据是否保留及是否存在重复控制。实物与仿真环境分别注明，不能以仿真结果代替实物接入结论。

| 场景 | 检查方法 | 预期结果 |
|---|---|---|
| 终端注册 | 两个终端分别注册，断开其中一个再连接 | 鱼塘归属及连接数正确，另一个终端仍可上传 |
| 环境数据上传 | 上传一条包含鱼塘、设备、时间和单位的有效测量 | 两端可查到同一记录，显示来源及更新时间 |
| 数据失效 | 提供过期或超量程的必需输入 | 标明无效原因，不生成有效投喂建议 |
| 日内数据整理 | 提供包含缺测和异常值的日内数据 | 保存原始曲线，正确标记异常，统计窗口与样本数可查 |
| 温度参与计算 | 使用同一测试规则，提供两组具有不同有效温度特征的输入 | 结果符合规则，能追溯特征窗口、原始输入和版本 |
| 正常投喂 | 有权限用户确认建议，终端返回完整执行反馈 | 同一任务依次更新状态，保留建议量、确认量和反馈 |
| 重复提交 | 重复提交同一请求及重复发送同一任务 | 只对应一个任务和一次执行，不重复统计 |
| 回执超时 | 任务下发后中断回执 | 显示待核查及原因，不自动再次投料 |
| 核查与恢复 | 分别核实已完成、未执行和仍不明的任务，再尝试新建任务 | 有权限者登记结论及依据；只有核查结束且设备满足恢复条件时解除占用 |
| 迟到与重复回执 | 核查后补发原任务回执，再重复发送并制造结论冲突 | 回执关联原任务，用料不重复累计，冲突进入再次核对并保留证据 |
| 实际量未知 | 设备返回完成但没有实际量 | 显示未获取，不以确认量冒充实测量 |
| 停止与卡料 | 请求停止或模拟卡料反馈 | 按设备反馈更新状态，保留异常和已知执行量 |
| 死鱼事件 | 登记疑似事件并分别完成确认及误报处理 | 各状态和处理记录可查，疑似数量不直接计入确认数量 |
| 权限限制 | 使用无控制权限账户提交任务 | 后端拒绝执行并返回原因 |
| 数据导入 | 导入两年 CSV，并重复导入相同文件 | 编号不冲突，重复记录按导入规则识别，来源可追溯 |
| 多塘比较 | 用另行准备的多塘测试数据切换、筛选及导出 | 同一时间和指标口径可对照，未授权鱼塘不出现 |
| 计划与运营 | 安排每日或每周任务，登记称重和用药 | 计划与实际可查，未完成任务和趋势统计一致 |
| 模型调用 | 用独立测试样本请求预测，再模拟模型失败 | 输出目标、单位、时间范围及版本明确，失败不返回伪预测 |
| 模型训练与测试 | 对已完成训练的模型，复查数据划分并复现独立测试和基准比较 | 版本、样本、处理方法、预测误差与基准结果可查；接口、流程和效果结论分别记录 |
| 视频与识别 | 切换水上水下画面，模拟离线和疑似事件 | 画面状态可辨，识别结果可追溯，人工核查记录保留 |

## 10 评审事项

本期设计范围按第2.3节执行，人工确认投喂、任务核查和疑似死鱼人工确认是当前流程。以下事项用于补齐实施条件；若评审决定调整范围，应同步更新功能、时序图和验收要求。

投喂规则需要明确适用鱼种和生长阶段、输入指标、单位、计算办法及建议有效期限。设备方面需要明确实物或仿真范围、投料机是否支持远程停止和实际量反馈、相机提供视频还是图像，以及死鱼识别是否属于本组算法任务。

数据方面需确定课程 CSV 的单位、单次或每日口径和批次划分，以及日内温度、溶氧特征的整理办法。ORP、摄食信号、用药、增重、成本及多塘比较需补充测试输入，并注明实测、模拟或人工登记来源。

算法方面，逐一列明投喂量、生长和水质预测所需的目标数据、可完成的训练任务、测试划分、基准及效果目标。缺少条件的模型按第2.3节注明当前交付程度。设备方面还需明确核查时可取得的执行记录、取消旧指令的方法与恢复依据，落实投喂核查权限。项目安排方面确定小组分工、提交日期与格式、部署环境和后端框架要求。
